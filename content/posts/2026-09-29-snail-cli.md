Obsidian の vault（Markdown ノートの集まり）に対して、ノートの起票・一覧・絞り込み・完了処理をコマンドラインからやる CLI を作って、10 か月ほど使っています。Rust 製で 12 ファイル・約 3,100 行、コミット 44 回。名前は `snail`（カタツムリ＝社名）です。

リポジトリは公開しています: [ymzkryo/snail-cli](https://github.com/ymzkryo/snail-cli)

うまく動いている話より、**設計のほころび**のほうが役に立つと思うので、そこを中心に書きます。結論を先に言うと、**いちばんたちが悪かったのは「成功したように見える失敗」**でした。

## なぜ作ったか

Obsidian にはテンプレート機能があります。ただ、面倒が残るのはテンプレートの中身ではなく**その前後**でした。

- ノートをどのディレクトリに置くか
- ファイル名にどう日付を入れるか
- プロジェクトノートの採番

毎回同じ frontmatter を書いて、同じ場所に置く。この作業が残ります。GUI を開いて、テンプレートを選んで、移動して、という手数が、思いついたことを書き留める障害になっていました。

## GTD の語彙をそのままサブコマンドにした

```console
$ snail --help
Commands:
  memo     Manage general memos
  todo     Manage todo tasks
  project  Manage projects
  gtd      GTD review and daily management
```

GTD（Getting Things Done）で運用しているので、`memo` / `todo` / `project` / `gtd` をそのまま並べています。**自分の頭の中の分類と、コマンドの分類を一致させる**のが狙いでした。ここは 10 か月経っても変えていないので、当たりだったと思います。

## 設計の基本：frontmatter を契約にする

CLI が読み書きするのは、**基本的に frontmatter だけ**です。本文には踏み込みません。

```yaml
---
title: タスクのタイトル
date: 2026-09-29
status: next
project: blog
estimate: 1h
---
```

`status` が `next` なら「今日やる」、`someday` なら「いつかやる」。**本文は人間のもの、frontmatter は機械のもの**という線引きです。

CLI がやるのは、設定された4つのディレクトリ（INBOX / NEXTACTION / いつかやる / プロジェクト）を走査して、**frontmatter の値で絞り込むこと**です。起票は INBOX 固定（`status: inbox`）で、完了時にアーカイブへ移すところだけディレクトリを動かします。status に応じた振り分けそのものは、別の仕組み（GitHub Actions）に任せています。

この線引きのおかげで、**CLI が想定する frontmatter の書式を保てば、本文は GUI から自由に編集できます**。逆に言うと書式のほうは自由ではありません。frontmatter のパーサーは簡易実装で、たとえば複数行形式のタグ一覧は読めません。

「基本的に」と書いたのは、**`gtd` 系だけが本文に踏み込んでいる**からです。日報の ToDo セクションを読む・書く、週報のレビュー節を読んで書き戻す、といった処理です。そしてそのうちの 1 つが壊れました（後述）。

### テンプレートはバイナリに埋め込まない

テンプレートは設定ファイルでパスを指すだけにしました。

```toml
# ~/.config/snail-cli/config.toml（抜粋）
[templates]
todo         = "~/templates/markdown/snip-todo.md"
daily_report = "~/templates/markdown/snip-daily-report.md"

[directories]
next    = "00100_NEXTACTION"
someday = "00500_いつかやる"
```

書式を変えたいときに**CLI を再ビルドしなくて済む**のが効きます。テンプレートは dotfiles の側に置いてあるので、そちらだけ直せば反映されます。

**これが後で刺さります。** 再ビルド不要という利点の裏で、**コードとテンプレートのあいだに暗黙の契約ができていました**。

## `--format json` が効いた

一覧にはフィルタと並び替えを付けました。

```console
$ snail todo list -f "status:next" --sort due --format json
```

このうち **`--format json` が、想定より広く効いています**。足したときのコミットには `--format json for scripting` と書いてあり、**スクリプトから呼ぶ用として入れたもの**です。

```
--format <FORMAT>
    Output format; json skips the interactive prompt
```

JSON を指定すると対話プロンプトを飛ばします。「スクリプト向け」として書いた性質が、そのまま **AI エージェント向け**になりました。いまは Claude Code のスキルが `snail todo list -f "status:next" --format json` を叩いて「今日やるべきタスク」を組み立てています。

エージェントに叩かせるつもりは無かったので、そこは想定外でした。ただ**「機械から呼べるようにする」という一段の抽象では、やることは同じ**でした。人間用と機械用を分けて考えなくてよかった、というのがここでの学びです。

## いちばん使うのは `todo done`

```console
$ snail todo done "path/to/note.md"
Marked as done: .../00100_NEXTACTION/2026-09-09-....md
Archived to: .../99999_アーカイブ/99991_task/2026-09-09-....md
```

`status` を `done` にして、**そのままアーカイブへ移動**します。「完了にする」と「片付ける」を 1 コマンドにまとめました。

地味ですが、これが一番効いています。2 手に分かれていると、`status` だけ変えて移動を忘れる日が必ず出るからです。

## Rust を選んだ理由

**起動が速いこと**だけです。1 日に何十回も叩くので、ここが体感に直結します。凝ったことはしていないので、言語の機能を使い倒しているわけではありません。

## ここからが本題：3 つのほころび

10 か月使って出てきた問題のうち、次の 3 つは **v0.3.2 の今も残っています**（直す予定です）。別に、直し終えたものが 1 つあるので、そちらは後ろの「4 つめ」に分けました。

### 1. プロジェクト名のタイポが検出できない

フィルタの検証は、実はちゃんと書いてあります。

```console
$ snail todo list -f "zzzkey:whatever"
Error: unknown filter key: "zzzkey"
  known keys: status, project, context, due, review
$ echo $?
1
```

キー名が未知なら、既知のキーを並べて `exit 1` で落ちます。`due:` に**日付でも対応キーワードでもない値**を渡したときも同じです。ここは気持ちよく動きます。

受理されるキーワードは `today` / `overdue` / `reached` / `missing`、それに `missing` の別名として `none` です。ただし**エラーメッセージは `none` を案内しません**（`expected … one of:` の一覧に入っていない）。これも小さな「ドキュメントと実装のずれ」で、記事を書くために叩いて初めて気づきました。

**抜けているのは値のほうです。**

```console
$ snail todo list -f "project:ZZZ_NOT_EXIST"
No active todos found.
$ echo $?
0
```

`project` のように**自由文字列を取るキーは、存在確認をしません**（`status` と `context` も同じで、`status:nxt` も黙って 0 件になります）。つまり **タイポと「本当に 0 件」が区別できません**。`-f "project:blg"` と打ち間違えたときに「そのプロジェクトのタスクは無い」と読んでしまいます。

しかも**ヘルプにはこう書いてあります**。

```
Unknown keys and values are errors, not empty results.
```

**「未知のキーと値はエラーになる。空の結果にはならない」。** キーについては本当ですが、**値については、少なくとも読み手にはエラーになると読めます**。

ソースのコメントのほうは、もっとはっきり約束していました。

```rust
/// Unknown keys and unsupported values are errors rather than silently
/// ignored, so a filter that cannot work never looks like "0 results".
```

**「動かないフィルタが『0 件』に見えることは決してない」。** `project:blg` はまさに、動かないのに 0 件に見えるフィルタです。**自分がコメントで約束したことを、自分で破っていました。**

**実は、これは 2 回目です。** この検証を足したコミット（2026-09-06）のメッセージに、こう書いてありました。

> `project:` was documented but never implemented, `context:` was ignored, and both silently returned every todo. Unknown keys and unsupported values were dropped without a word, **so a broken filter looked like a working one.**

**「壊れたフィルタが、動いているフィルタに見えた」。** 当時すでに同じ失敗を踏んで、同じ言葉で書いていたわけです。`project:` は**ヘルプに書いてあるのに実装されていなかった**。

そこでキーと日付の検証を入れました。ところが**自由文字列の値は手つかずのまま、ヘルプには「値もエラーになる」と書いた**。直したぶんだけドキュメントを前に進めて、直していないぶんも一緒に約束してしまった形です。

**症状は逆でした。** 1 回目は全件が返り（コミット本文の "silently returned **every** todo"）、2 回目は 0 件が返ります。それでも **ヘルプが実装より先に約束していた**点は同じです。1 回目は「実装していないものを書いた」、2 回目は「半分しか直していないのに全部直したと書いた」。

症状が違うのに同じ構造で転んだ、というのが正直なところです。**ヘルプを読んだ人ほど「空なら本当に 0 件だ」と信じます。**

自分で叩いているときは気づきます。困るのは **`--format json` で機械から呼ぶとき**です。人間なら「あれ、あるはずだけど」と思う場面が、黙って空配列で通ります。

キー名の検証を書いたときに、値のほうは「自由文字列だから」で済ませていました。**検証を書いた気になっていた**わけです。

### 2. 成功したように見える失敗

一番たちが悪かったのがこれです。`snail gtd today add "タスク"` は日報の ToDo セクションに 1 行足すコマンドなのですが、**タスクを足さないまま「成功」と出力していました**。

原因は `if` の 1 行です。

```rust
if line.trim() == "## TODO" {
```

**`## TODO` を完全一致で探しています。** ところが実際の日報の見出しはこうです。

```markdown
## ✅ 今日のToDo
```

**ここで話がつながります。** CLI に内蔵してある既定テンプレートの見出しは、ちゃんと `## TODO` です。

```rust
// 日報が無いときに使う既定テンプレート（抜粋）
"---\ndate: {}\n---\n\n# {} Daily Report\n\n## TODO\n\n## Done\n\n## Memo\n",
```

つまり**内蔵テンプレートのままなら動きます**。壊れたのは、テンプレートを外に出して、その見出しを `## ✅ 今日のToDo` に変えたからです。

さきほど「テンプレートを外に出したから再ビルドが要らない」と書きました。その裏で、**コードは本文の見出しを決め打ちで探している**という暗黙の契約が残っていました。テンプレートだけ直せる自由は、**その契約を黙って切る自由**でもありました。

**そして、同じファイルの読む側はこうなっています。**

```rust
// Match various TODO section headers
let line_lower = line.to_lowercase();
if line.starts_with("## ") && (line_lower.contains("todo") || line.contains("ToDo")) {
```

`## ` で始まって `todo` を含めば通す、というゆるい判定です。コメントに「various TODO section headers」とあるとおり、見出しが揺れることを見越しています。だから `gtd today list` は `## ✅ 今日のToDo` をちゃんと読めます。

履歴を見ると、順番はこうでした。

| | |
|---|---|
| 2025-12-01 | 初期コミット。**書く側**が `== "## TODO"` の完全一致で入る |
| 2025-12-31 | `gtd today list` を実装。**読む側**を最初からゆるく書く |

つまり**あとから書いた側だけが揺れに強くなって**、先にあった書く側はそのまま残りました。一覧では ToDo が見えているのに、追加だけが黙って失敗する。同じファイルの中で判定が食い違っていたわけです。

**片方を書くときに、対になるもう片方を見ていませんでした。**

見出しが一致しないとセクションが見つからず、挿入位置が決まりません。すると**タスクを足さないまま書き戻します**（`lines()` で分解して `join("\n")` で組み直すので、末尾の改行が落ちるくらいの差しかありません）。そして、

```rust
    fs::write(&file_path, updated_content)
        .with_context(|| format!("Failed to update daily report: {:?}", file_path))?;

    println!("Added task to daily report: {}", task);
```

**書き込みのエラー処理はちゃんと書いてあります。** `with_context` でメッセージまで付けている。それでも、**足せたかどうかは見ていません**。`println!` が無条件です。

本質は戻り値の型でした。挿入する関数のシグネチャはこうです。

```rust
fn add_to_todo_section(content: &str, task: &str) -> String {
```

**`String` を返すだけで、「見つからなかった」を伝える手段がありません。** 関数の中には `task_added` というフラグがあります（1 回だけ挿入するための制御です）が、**関数の外へは返していません**。呼び出し元の `today_add` は `Result` を返す形にしてあるのに、そこへ伝わる経路が無い。エラーハンドリングを書いたつもりで、**判定の結果を運ぶところを書き忘れている**形でした。

**静かに失敗するより、成功したと言って失敗するほうが悪い**と思い知りました。とくにスクリプトやエージェントから呼んだときは、成功表示だけが返ってきます。

人間が叩いたときは、実は気づける経路があります。このコマンドは成功メッセージのあとエディタを開くので、日報がその場で目の前に出るからです。もっともその挙動は、次に書くほころびそのものです。

### 3. エディタを無条件で開く

作った当初は、ノートを起票したら続けて書くのが当然だと思っていたので、**生成後に必ずエディタを開く**実装にしました。

スクリプトから呼ぶとそこで止まります。あとから `-n, --no-edit` を足して回避しました。

```console
$ snail todo new --help
    -n, --no-edit            Do not open editor after creating
```

ただし足したのは **`memo new` / `todo new` / `project new` の 3 つ**、つまり「起票する」コマンドだけです。**`gtd today add` には今も付いていません**（`snail gtd today --help` にオプションが出てきません）。

**自分がスクリプトから呼んで困ったところだけ塞いだ**ことが、そのまま残っています。

## 4 つめ：`00500_いつかやる` を見ていなかった

これは 5 日前（2026-09-24）に見つけて直したものです。`snail todo list` が **`00500_いつかやる/` ディレクトリを走査していませんでした**。

面白いのは、**設定には最初から入っていた**ことです。`someday_dir()` という関数が config にあるのに、一覧を組み立てる側がそれを呼んでいませんでした。使われないまま 10 か月経っていたわけです。

直したのは 60 行ほどの変更でした（[PR #11](https://github.com/ymzkryo/snail-cli/pull/11)）。

これは 1〜3 とは種類が違います。**自分の運用が後から変わったこと**が原因です。作った当初は「いつかやる」を CLI で見る発想がなく、あとから GTD の回し方を変えて `someday` を定期的に見直すようになりました。道具の側がついてきていなかった。

**運用を変えたあとも、CLI の走査対象を見直していませんでした。**

## 配布は中途半端です

**crates.io には公開していません。** 一方で GitHub Releases には Linux 向けバイナリを出すワークフローがあり、v0.3.0 から v0.3.2 までタグは並んでいます。

README の手順は clone してビルドするだけなので、**実態と案内が合っていません**。`cargo install --git` でも入るはずですが、そこは確かめていません。ここも「ドキュメントが実装に追いついていない」側の話です。記事にするなら直しておきたかったのですが、**直してから書くと結局書かない**ので、このまま出します。

`memo search` / `project show` / `gtd monthly` の 3 つは、`not yet implemented` と表示するだけの空実装が残っています。`todo list` のフィルタで足りてしまったので、埋めないまま 10 か月経ちました。

それでも、起動が速くて自分の運用にぴたりと合う道具が手元にあるのは快適です。費用対効果で言えば、作ってよかったと思っています。ほころびを見つけるたびに直せるのも、自分で書いたものの利点ではあります。

## まとめ

- **GTD の語彙をそのままサブコマンドにした**のは 10 か月変えていない。自分の頭の中の分類とコマンドの分類を一致させると、覚えるものが減ります
- **frontmatter を契約にして本文に踏み込まない**と、**CLI が想定する書式を保つかぎり**本文は GUI から自由に編集できます。逆に、**本文に踏み込んでいた `gtd` 系で壊れました**
- **テンプレートをバイナリに埋め込まない**と、書式を変えるのに再ビルドが要りません。ただし**本文の見出しを決め打ちで探すコードとは契約が切れやすい**。テンプレートだけ直せる自由は、その契約を黙って切る自由でもありました
- **`--format json` を足すと、人間用の道具がそのまま機械用の道具になります**。ただし**雑なエラー処理の害も同時に大きくなります**。人間なら気づくタイポが、機械から呼ぶと黙って通ります
- **片方を書くときに、対になるもう片方も見る。** あとから書いた読む側だけが見出しの揺れに強くなり、先にあった書く側は完全一致のまま。**一覧には出るのに追加だけ失敗する**状態になっていました
- **ヘルプに書いた保証は、実装より強く信じられます。** しかも私はこれを **2 回**やりました。1 回目は実装していない `project:` をヘルプに書き、2 回目は半分しか直していないのに「値もエラーになる」と書いた。**直したぶんだけドキュメントを進める**のが正しかったです
- **「成功したように見える失敗」が一番こわい。** 静かに失敗するなら結果を見に行けますが、「やりました」と表示されると見に行きません。呼び出し元が `Result` を返す形にしていても、**判定した結果を運ぶ経路が無ければ意味がない**です（フラグを関数の中で捨てていました）
- **自分で困ったところだけ塞ぐと、同じ穴が別のコマンドに残ります**（`--no-edit` を `new` 系 3 つにだけ足して、`gtd today add` を忘れた）
- **運用を変えたら、一覧が拾う対象も確認する。** 設定に関数だけあって呼ばれていない、という形で 10 か月眠っていました
- 持ち帰りを 1 つに絞るなら、**成功を表示する前に、目的の変更ができたかを判定する**。これだけで今回のいちばん痛い穴は塞がります
