Obsidian の vault を GitHub リポジトリにして、タスク管理を GitHub Actions と CLI と AI エージェントで回しています。ノートは 5,269 件、Python のスクリプトが 21 本、workflow が 20 本あります。

ノート置き場そのものは 2019 年から使っていますが、自動化を載せたのは 2025 年 11 月からです。この 11 か月で、効いた判断と効かなかった判断がだいぶはっきりしました。

いちばん時間がかかったのは、**書いた規約を機械に守らせるところ**でした。ファイルを動かすスクリプトは最初の月からあったのに、**規約を検査するスクリプトを書けたのは 10 か月あとの 2026 年 9 月**です。タグを 93 種類まで増やしてしまっていて、**何を正しいとするかが決まっていなかった**からです。

## ノートの約 85% は、自動生成・取り込みの記録系

数だけ見せると大きく見えてしまうので、先に内訳を出します。`type/` タグで分けると、こうなっています。

| `type/` | 件数 | 中身 |
|---|---:|---|
| `study` | 1,133 | 学習記録（自動生成） |
| `meal` | 1,072 | 食事の記録（自動生成） |
| `health` | 671 | 体組成・血圧（自動取り込み） |
| `daily` | 550 | 日報（自動生成） |
| `clip` | 498 | web クリップ（自動取り込み） |
| `running` | 469 | ランニング（Strava から取り込み） |
| `todo` | 404 | タスク |
| `tech` | 118 | 技術メモ |
| `meeting` | 82 | 面談・議事録 |
| `reference` | 80 | 倉庫のリスト類 |
| `weekly` | 55 | 週報（自動生成） |
| `analytics` | 44 | アクセス解析のレポート（自動生成） |
| `wish` | 38 | いつかやる |
| `idea` | 34 | ネタ・アイデア |
| `monthly` | 12 | 月報（自動生成） |
| `book` / `trip` / `mail` | 9 | 書籍・出張・メールのクリップ |

自動生成と自動取り込みの分類を足すと 4,504 件で、**ファイル数の約 85%** です。

これは分類別のファイル数の話で、**誰が書いたかの集計ではありません**。自動生成された日報に人があとから追記することもあるので、残りを「人が書いた件数」と言うことはできません。

`status` に値が入っているノートは 441 件です。ただしそのうち 368 件は完了か取りやめで、**いま動いているのは 73 件**でした（`someday` 28 / `next` 25 / `scheduled` 14 / `waiting` 4 / `inbox` 1 / `inprogress` 1）。

## タスクの状態は status に集約している

タスクまわりの中心は frontmatter の `status` です。

```yaml
---
title: サンプルアプリの説明を書く
date: 2026-10-11
status: next
project: example-project
estimate: 1h
tags: [type/todo]
---
```

トップレベルは数字のプレフィックスで GTD のフェーズを表しています。

```
00000_INBOX/        捕まえたばかりのもの
00100_NEXTACTION/   今すぐ着手できるもの
00200_技術メモ/
00300_倉庫/
00400_webクリップ/
00500_いつかやる/
00600_面談資料/
00700_メモ/         日報・週報・記録系
00800_プロジェクト/  プロジェクトごとの棚
00900_files/
99999_アーカイブ/
```

`status` を書き換えると、次に走った workflow がファイルを動かします。

```
status: next       →  00100_NEXTACTION/ に出てくる
status: done       →  99999_アーカイブ/ へ引っ込む
```

ただし**配置は `status` だけでは決まりません**。`project` が入っているタスクを `scheduled` や `waiting` にすると、`00800_プロジェクト/` の該当する棚へ移ります。`project` が空のままだと移る先が決まらないので動きません。通知や昇格では日付も見ます。

それでも、人がやるのはテキストを 1 行変えることだけです。Obsidian で開いていてもエディタで開いていても同じで、frontmatter を 1 行いじって push すれば、残りは Actions がやります。ドラッグでファイルを動かす操作が消えたのが、思っていたより大きい効果でした。

## 分けているのはキーではなく、値

この記事を書くために自分のメモを読み直して、1 か月前に書いた説明が間違っていたことに気づきました。

ネタ用のメモには「`status` の有無で memo と todo を判定している」と書いてありました。これは違っていて、全 5,269 件が `status:` というキーを持っています。ノートのテンプレートに最初から入っているからです。

**分けているのは値の有無でした。**

```yaml
status:          # 値が空 → タスクとしての状態判定から外れる
status: next     # 値がある → タスクとして扱う
```

通知のスクリプトも、まず `status` に値があるかを見てからタスクを集めています。キーがあるかどうかで判定していたら、全ノートがタスク扱いになって破綻していたはずです。**間違っていたのはメモのほうです。**

## 自動化は前から動いていた。止まっていたのは検査のほう

ここが今回いちばん書きたかったところです。

自動化の履歴はこうなっています。

| 時期 | 入れたもの |
|---|---|
| 2025-11 | 日報の生成、日付によるファイル整理 |
| 2026-01 | タグを見てファイルを振り分ける処理 |
| 2026-03 | `status` に連動した自動移動 |
| 2026-09 | タグ語彙の統制、`type/` の必須扱い、検査スクリプト |

**スクリプトは早い段階から動いていました。** タグを見て振り分ける処理は 2026 年 1 月から、`status` 連動の移動は 3 月からあります。だから「タグを絞ったから自動化が動き出した」のではありません。

無かったのは**検査**です。タグは自由に付けていたので 93 種類まで増え、似た意味のタグが分散して、タグから何かを探すことが無くなりました。そして何より、**この状態では「タグが正しいか」を検査できませんでした。** 正しさの基準が無いからです。

2026 年 9 月に体系を切り直しました。そのときのコミットメッセージにこう残っています。

```
## 適用
- 既存42ファイルを新体系へ移行（93タグ → 統制語彙へ集約）
- 自動生成ノート 3,773件に type/ を一括付与
- webクリップ本体 113件に type/clip を付与
- tags: の記法をインラインに統一（YAML リスト形式 166件を移行）
  レガシータグ66種を寄せ、clippings 145件は温存
```

やったことは 2 つです。**軸を 2 つに決めて、語彙を設定ファイルに固定しました。**

- `type/` は必須でひとつ。「何のノートか」を表す
- `topic/` は 0 個から 4 個まで。「何についてか」を表す

```toml
[tags]
# 軸1: type/ — 必須1つ。「何のノートか」
types = [
    "daily", "weekly", "monthly",
    "meal", "health", "running", "study", "clip",  # 自動生成される記録系
    "tech",       # 技術メモ・調査記録
    "todo",       # TODO ノート
    "meeting",    # 面談・定例・議事録
    # …
]
```

切り直した時点では `type/` 16 語と `topic/` 29 語の 45 語でした。いまは 19 語と 30 語の 49 語に増えていて、別枠で機能タグの `clippings` を 1 つ残しています。

**検査のスクリプトが入ったのも同じ日です。** 語彙を設定ファイルに固定したコミットと、`type/` を全ノートに付与して必須扱いにしたコミットと、検査スクリプトを足したコミットが 2026 年 9 月 5 日に並んでいます。別々のコミットですが、順番が逆にはできませんでした。**93 種類のままでは、何を正しいとするかを書けないので検査が書けません。** 語彙が設定ファイルの 1 箇所にあると、検査スクリプトと生成スクリプトが同じ出所を読めます。

**効いたのは語彙の数を減らしたこと自体より、意味と出所が揃ったことでした。** 数はその後 45 から 49 に増えていますが、検査は壊れていません。増やすときに設定を直すからです。

## waiting と scheduled はボールの所在で分ける

語彙を絞ると、こんどは「どの値を使うか」で迷うようになります。8 つしかないので、ひとつひとつの意味がはっきりしていないと手が止まります。

いちばん取り違えたのが `waiting` と `scheduled` でした。どちらも「今は着手しない」ので、感覚で選ぶと混ざります。

**ボールが誰にあるかで分ける**、という形に落ち着きました。

| `status` | 意味 | ボール |
|---|---|---|
| `inbox` | 未処理。まだ何をするか決めていない | 自分 |
| `next` | 今すぐ着手できる次の行動。まだ手を付けていない | 自分 |
| `inprogress` | 着手して、まだ終わっていない | 自分 |
| `waiting` | 他人の返答・作業を待っている。自分の次の行動が無い | 相手 |
| `scheduled` | 自分がやるが着手日が先。日付が来たら `next` になる | 自分 |
| `someday` | いつかやる。日付は決めていない | 自分 |
| `done` / `canceled` | 完了 / 取りやめ | - |

迷ったときは**「今この件で、自分が次の行動を取れるか」**を問うことにしています。取れるなら `next`、相手の返答が必要なら `waiting`、着手日がまだ先なら `scheduled` です。

`next` と `inprogress` は作業の痕跡があるかで分けています。ブランチを切った、PR を開いた、下書きを書いた、ならもう `inprogress` です。頭の中で考え始めただけなら `next` のままにします。

この表は規約ファイルに置いていて、**スキル側は参照するだけで意味を書き写さない**ようにしています。2 箇所に書くと片方だけ古くなるので。

## WIP の上限は、数を抑えるためではなく名指しするために置いた

`inprogress` を導入したとき、同時に手を付けている数に上限を置くかどうかで迷いました。2 週間ぶん観測してから決めることにして、`project` ごとに 1 件までという形にしました。

ただし**この観測は、上限の根拠としてはあまり使えませんでした。**

日報に記録された件数は最大 3 件、平均 1.3 件で、ゼロの日が 5 日ありました。ところがふりかえりの記録を読み直すと、**ゼロの日は作業が無かったのではなく、着手しているのに状態を更新していなかった日**でした。さらに、同じ `project` に `inprogress` が 2 件ある日も複数ありました。設計上の上限は観測期間中に破れています。

つまり件数の集計は、**実際の並行作業数を表していませんでした。** 更新漏れを含む数字で「多すぎて困る場面が無かった」とは言えません。

それでも `project` ごとに 1 件という形は残しています。理由は数の抑制ではなく、**何に着手しているかを名指しさせるため**です。1 件に絞ると「いまこの案件で手を付けているのはこれ」と書かざるを得なくなります。

**ここは観測の設計を間違えました。** 「上限を決める材料を取る」つもりで件数を数えたのに、数えていたのは状態の更新状況でした。記録が実態からずれる前提を置いていなかったのが原因です。

似た判断を `estimate` でもしています。見積もりは `2min`・`5min`・`30min`・`1h`・`2h` の 5 段階で、上限の `2h` に収まらないものは分解の合図として扱います。**ここで語彙を広げて `4h` を足すと、粒度のチェックとして効かなくなります。** だから広げずに、着手後に見積もりが膨らんだ場合は本文へ残りの工数を書くほうに倒しました。

## 自動で直すのは、直し方が一意に決まるものだけ

検査のスクリプトがあって、frontmatter の形式、ファイル名の規約、タグが語彙に入っているかを見ています。push のときに workflow の中で走り、**違反があれば Slack に通知します**。GitHub の required status check のようにマージを止める仕組みではありません。ここで言う「必須」は `type/` を全ノートに付けるという規約の話です。

**自動で直すのは、直し方がひとつに決まるものだけに限っています。** 実装されているのは次の 7 つです。

- キーのコロン直後に空白を補う
- `tags` のリスト記法をインラインへ統一する
- キー行の末尾の空白を除去する
- `status` / `context` / `estimate` の末尾コメントを除去する
- `@` やバッククォートで始まる値をクォートする
- 正規キーの欠落を補う
- `project:` の表記揺れをディレクトリの実名に寄せる

判断が要るものは直しません。報告して止めます。

たとえば語彙外の `estimate` は、`45min` のような「上限以内の表記ゆれ」と `4h` のような「上限を超えた分解の候補」に分かれます。前者は切り上げて揃え、後者は触らない、という方針にしています。**これは運用の方針で、検査スクリプトが自動で振り分けているわけではありません。** 後者を機械が書き換えてしまうと、**「分解しろ」という合図が消えてしまいます。**

2026 年 9 月に数えたときは、`next` と `inprogress` の 35 件のうち 11 件が語彙外でした。これを一括で揃えるスクリプトは書けますが、書いていません。**語彙外の中身は表記ゆれと分解が必要なものが混ざっていて、どちらかは読まないと分かりません。** そこは人がやる部分だと思っています。

## 生成・整理・検査・通知で役割を分ける

21 本のスクリプトを役割で分けると、だいたい 4 つと、おまけの 2 つです。

- 生成: 日報・日次 TODO・関連ノートのリンクを作る
- 整理: `status` と `project` を見てファイルを動かす
- 検査: frontmatter・ファイル名・タグ語彙を検査して、構造だけ直す
- 通知: 期限・レビュー日・いつかやるの棚卸しを Slack へ
- 収集: 睡眠・運動・体組成・アクセス解析を外部 API から取り込む
- 昇格: 着手日が来た `scheduled` を `next` に上げる

実行の起点はばらばらです。生成は JST 00:05 の予定、整理は 23:55 の予定、通知は 07:00 の予定で、タスクの整理と検査は push 起点です。

なお `schedule` の指定は予定時刻で、その時刻の実行を保証するものではありません。遅延することもドロップされることもあります。そこで一度こけた話は[別の記事](/2026/09/19/scheduled-workflow-silently-stops/)に書きました。

参考: [Events that trigger workflows - GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

責務は細かく分けています。昇格のスクリプトは `status` を書き換えるだけで、ファイルの移動はしません。 移動は整理のスクリプトの仕事です。分けておくと、昇格の条件を変えたいときに移動のロジックを読まなくて済みます。

frontmatter を読み書きする CLI も Rust で書いていて、`snail memo new` や `snail todo list` で起票と絞り込みをしています。こちらは[別の記事](/2026/09/29/snail-cli/)に書いたので、ここでは触れません。

Claude Code のスキルも vault に入れて Git で管理しています。トップレベルで 5 個、`SKILL.md` の枚数で数えると 13 枚です。ふりかえりや分解の手順をスキルとして置いておくと、同じ手順を別の日にも同じようにたどれます。

## 「なんちゃって」と呼んでいる理由

GTD の原典どおりにはやっていません。

週次レビューは自動の通知に頼っていて、腰を据えて全体を見直す時間は取れていません。コンテキスト（`@computer` のような実行場所のタグ）は項目としては持っていますが、絞り込みにはほとんど使っていません。2 分ルールもありません。

捕まえる・置き場所を決める・出てくるようにする、までは回っていて、**見直すところが弱い**、という状態です。

## まとめ

- Markdown のノート置き場を Git リポジトリにすると、frontmatter の 1 行を変えるだけで配置が付いてくる仕組みが組めます。ただし配置は `status` だけでなく `project` や日付とも組み合わせて決まります
- ファイルを動かすスクリプトは、タグを整理する 10 か月前から動いていました。整理して変わったのは**検査を書けるようになったこと**です。語彙の基準が無いと、正しさを機械に判定させられません
- 効いたのは語彙の数を減らしたこと自体より、**意味と出所が 1 箇所に揃ったこと**でした。その後 45 語から 49 語に増えていますが、検査は壊れていません
- 語彙を絞ると使い分けで迷うので、判断の軸を言葉にしておく必要が出てきます。`waiting` と `scheduled` はボールが誰にあるかで分けました
- WIP の上限は「2 週間測って決めた」と言いたかったのですが、**その観測は状態の更新漏れを含んでいて上限の根拠に使えませんでした**。制約が残っているのは、数を抑えるためではなく着手中のものを名指しさせるためです
- 自動で直すのは直し方が一意に決まるものだけにして、判断が要るものは報告で止めると、分解の合図が消えません
- ノートの約 85% は自動生成・取り込みの記録系です。これはファイル数の内訳で、誰が書いたかの集計ではありません
